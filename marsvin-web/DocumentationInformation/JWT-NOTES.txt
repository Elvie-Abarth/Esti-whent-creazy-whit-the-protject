MARSVIN AND JWT - COOKIES FOR THE WEBSITE, JWT FOR THE API
==========================================================

SHORT ANSWER
------------
The website itself logs in with a cookie, not a JWT (JSON Web Token) - the
reasons are below. Next to it there is a small JSON API under /api that
uses JWT bearer tokens, so both are in the project and each is used where
it fits. The cookie login was left alone: the API was ADDED beside it, the
way the last section of this file always recommended.

  Website pages   cookie login (email link, optional authenticator code)
  /api/*          "Authorization: Bearer <JWT>"

For how the cookie login itself works (the email link, 2FA, session
limits, the security stamp), see WEBSITE-ARCHITECTURE.md, section 4.


WHAT JWT IS FOR
---------------
JWT is a stateless way to authenticate between a client and a server. The
course material describes it for one particular setup: a separate
frontend (for example Vue.js) that calls a REST API. The frontend logs
in, gets a token back, stores it, and sends it in an "Authorization:
Bearer ..." header with every API call.

A JWT has three parts, separated by dots:

  Header     - which algorithm signed it, e.g. { "alg": "HS256", "typ": "JWT" }
  Payload    - the claims: who the user is, their role, when it expires
  Signature  - a hash of header + payload made with a secret key, so the
               server can tell if anything was changed

Header and payload are only Base64Url-encoded, not encrypted. Anyone who
holds the token can read them.


WHY MARSVIN IS NOT BUILT THAT WAY
---------------------------------
Marsvin is an ASP.NET Core Razor Pages site. The server builds the
finished HTML page and sends it to the browser; there is no separate
frontend application and no API for one to call. In that setup the
browser only needs a login cookie, which it sends by itself on every
request. A token that JavaScript has to store and attach by hand would
add work and risk without solving anything.


THE SAME IDEAS, IN COOKIE FORM
------------------------------
Everything a JWT carries has a counterpart in Marsvin's login cookie:

  JWT concept                         What Marsvin does
  ----------------------------------  ------------------------------------------
  Payload with claims                 The cookie holds the same kind of claims:
  (user id, name, role)               user id, email, display name and role

  Signature, so the token             The cookie is signed AND encrypted by
  cannot be changed                   ASP.NET Core's data protection - it cannot
                                      be changed, and it cannot even be read

  "exp" (expiration)                  30 minutes of inactivity, 8 hours at most

  [Authorize] and roles               [Authorize(Roles = "...")] on pages, plus
  on API endpoints                    deny-by-default for every page

  Token sent in the                   Cookie sent automatically by the browser
  Authorization header

The claims are built in one place: Data/AuthCookiePrincipal.cs.


WHERE THE COOKIE APPROACH IS STRONGER HERE
------------------------------------------
1. Logging out actually works.
   A JWT is stateless: once issued it stays valid until it expires, and
   the server has no way to take it back. Marsvin looks the account up in
   the database on every request (AuthCookiePrincipal.RevalidateAsync),
   so these take effect on the very next click:
     - an admin deactivates or deletes the account
     - the role is changed
     - the password is changed or reset (the security stamp changes)
     - the user presses "log out everywhere"
   With plain JWT none of this is possible without adding a server-side
   list of revoked tokens - which makes it stateful again.

2. JavaScript cannot read the login.
   The cookie is HttpOnly. In the typical JWT example the token is kept
   in localStorage, where any script on the page can read it - so a
   single XSS hole means a stolen login.

3. The contents are hidden.
   A JWT payload is readable by anyone who has the token. The cookie is
   encrypted, so the claims are not visible to the browser's user or to
   anything that intercepts it.

THE TRADE-OFF
A cookie is sent automatically, which is what makes cross-site request
forgery (CSRF) possible; a token in a header is not sent automatically
and does not have that problem. Marsvin covers it with the antiforgery
token that every form post requires, and SameSite=Lax on the cookie.

Neither approach is "the secure one". JWT fits an API used by a separate
frontend, a mobile app or another service. Cookies fit a server-rendered
site. Marsvin is the second kind.


WHAT IS WRONG WITH THE TYPICAL EXAMPLE CODE
-------------------------------------------
The step-by-step JWT guide in the course material (the ChatGPT-written
C# + Vue.js one) shows the idea well, but several things in it should not
be copied into real code:

  - The secret key is written in the source ("SuperSecretKey123456789!").
    Anyone who sees the code can forge a token for any user, including
    an admin. A key belongs in user-secrets or an environment variable.

  - ValidateIssuer = false and ValidateAudience = false.
    A token made for a different system that happens to share the key
    would be accepted.

  - RequireHttpsMetadata = false.
    Allows the token to travel over plain HTTP, where it can be read.

  - The token is stored in localStorage (the XSS risk described above).

  - Dummy login (username "test", password "password") and no password
    hashing.

  - No way to revoke a token and no refresh tokens, so the choice is
    between long-lived tokens (risky if stolen) and logging in again
    every hour.

  - The key is created with Encoding.ASCII from a short string. HS256
    needs at least 256 bits of real randomness to be safe.


THE JWT API THAT WAS ADDED
--------------------------
Code: Data/JwtTokens.cs (key, token creation, per-request account check),
Data/ApiEndpoints.cs (the endpoints and role policies), and the AddJwtBearer
block in Program.cs. Tests: Pages/Account/EndToEndJwtApiTests.cs and
Data/JwtSettingsTests.cs.

How a client gets and uses a token:

  1. Sign in on the website as usual (password, email link, authenticator
     code if the account has one).
  2. POST /api/auth/token with that session's cookie. The answer is
     { "token": "...", "tokenType": "Bearer", "expiresAt": "..." }.
  3. Send "Authorization: Bearer <token>" on every /api call.

Endpoints:

  POST /api/auth/token   needs the login cookie; hands out a token
  GET  /api/me           any role - who the token says you are
  GET  /api/orders       any role - the caller's OWN orders
  GET  /api/orders/{id}  the caller's own order, otherwise 404
  GET  /api/admin/orders Admin and Employee
  GET  /api/admin/users  Admin only

Choices, and why they differ from the course example:

  - The token comes from an existing website session, not from a
    username-and-password endpoint. A password-only endpoint would be a way
    round the email-link step and the authenticator code, which would make
    the API the weakest door into every account. Rate limiting ("auth"
    policy) still applies to the token endpoint.

  - The key is Jwt:Key from user-secrets or an environment variable, at
    least 32 bytes (set it with: dotnet user-secrets set Jwt:Key <random>).
    Outside Development the app refuses to start without it; in
    Development it makes a random key for each run, so tokens die when the
    app restarts. No key is in the source.

  - Issuer and audience are both set and validated, the algorithm is pinned
    to HS256 (a token cannot ask for "none"), the lifetime is 15 minutes and
    clock skew 30 seconds. HTTPS is required outside Development.

  - Tokens CAN be called back, which the course example cannot do: on every
    request the account is looked up again. A token stops working when the
    account is deactivated or deleted, when its password changes (the
    security stamp, same as the cookie), or when its role changed - the
    role is taken from the database, so a demoted Admin loses /api/admin at
    once even though the token still says Admin.

  - There are no refresh tokens. A client that needs a new token asks again
    with a live website session, so ending that session (logout, "log out
    everywhere", password change) ends the ability to get more.

  - The token holds id, name, email, role and the stamp - never the password
    hash. It is only signed, not encrypted, so anyone who has it can read it.

  - The two schemes never mix. The pages ignore bearer tokens, and /api
    ignores the cookie, so a forged form post from another site cannot act
    through a visitor's cookie on the API. /api answers a bare 401/403/404 as
    JSON clients expect, not the website's HTML error page.

  - Where the client keeps the token is the client's business. The
    localStorage risk described above is the reason this project does not
    ship a JavaScript client that stores one.

Trying it by hand (PowerShell, site running, signed in in a browser):
copy the auth cookie from the browser's developer tools, then

  $t = (Invoke-RestMethod -Method Post http://localhost:5080/api/auth/token `
        -Headers @{ Cookie = ".AspNetCore.Cookies=<value>" }).token
  Invoke-RestMethod http://localhost:5080/api/me -Headers @{ Authorization = "Bearer $t" }

Still true, and honest: this is a small demonstration API. There is no
CORS configuration (so a browser frontend on another origin cannot call it),
no token revocation list beyond the account checks above, and no refresh
tokens.
